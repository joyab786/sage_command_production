# SageCommand V3 — What-If Simulation Intelligence Foundation (Prompt 28)

## 1. Product Objective & Executive Summary

The **What-If Simulation Intelligence Foundation** provides an analytical counterfactual simulation layer for the SageCommand V3 Industrial Operations AI OS. It enables factory managers, process engineers, reliability technicians, and supply chain analysts to construct deterministic, hypothetical operational scenarios and simulate their downstream analytical impacts before real decisions are made.

Typical counterfactual questions answered deterministically by this system:
- *What if factory demand surges by 20% over the next 7 days?*
- *What if supplier capacity drops by 15% due to an upstream disruption?*
- *What if machine degradation accelerates, increasing vibration by 25%?*
- *What if asset availability decreases by 10% on a bottleneck assembly line?*
- *What if correlated conditions (e.g., demand surge + supplier delay) occur simultaneously?*

### Cardinal Execution Invariant

> **CRITICAL ARCHITECTURAL RULE:**
> What-If Simulation produces **hypothetical analytical outcomes**.
> It does **NOT** execute, approve, mutate, or trigger operational, control, financial, procurement, inventory, or physical systems.
> It never invokes `ExecutionGateway`, `Action API`, PLC writes, robot commands, work order dispatches, or inventory adjustments.

```text
REAL OBSERVATIONS
      ↓
DATA QUALITY
      ↓
ANOMALY / SENSOR FUSION / EVENTS
      ↓
ONTOLOGY / KNOWLEDGE GRAPH / DIGITAL TWIN
      ↓
BASELINE STATE
      ↓
HYPOTHETICAL SCENARIO
      ↓
WHAT-IF SIMULATION
      ↓
SIMULATED OUTCOME
      ↓
DELTA / IMPACT / UNCERTAINTY
      ↓
EVIDENCE + EXPLANATION
      ↓
HUMAN DECISION
```

## 2. Architectural Principles & State Classifications

The simulator explicitly separates five epistemological states for any operational metric:

1. **Observed**: What actually occurred in the physical facility based on trusted sensor observations, SCADA telemetry, or confirmed transaction logs.
2. **Derived**: Numerically or logically calculated from verified observed evidence using deterministic formulas.
3. **Simulated**: A hypothetical counterfactual state generated by applying an explicit scenario transformation onto an established baseline.
4. **Estimated**: A model-based approximation when direct telemetry or evidence is incomplete or indirect.
5. **Unknown**: A metric or parameter that cannot be responsibly or defensibly determined from existing data or factors.

### Invariant Rules on State Transformations

Under NO circumstances will the engine silently perform:
- `UNKNOWN → 0`
- `UNKNOWN → OBSERVED`
- `SIMULATED → OBSERVED`
- `ESTIMATED → OBSERVED`

Every simulation output preserves complete, immutable provenance (`SensorValueProvenance.SIMULATED`).

## 3. Strongly Typed Scenario Contract

The scenario architecture is defined in `backend/data/schemas/what_if_simulation_contract.py`:

- **`SimulationTarget`**: Identifies target entity (`entity_id`), type (`entity_type`), and scope (`ENTITY`, `LINE`, `PLANT`, `SYSTEM`, `NETWORK`).
- **`ScenarioVariable`**: Strongly typed parameter modification. Disallows arbitrary executable expressions.
  - Types: `DEMAND_CHANGE`, `SUPPLY_CAPACITY_CHANGE`, `LEAD_TIME_CHANGE`, `ASSET_AVAILABILITY_CHANGE`, `ASSET_DEGRADATION_CHANGE`, `PROCESS_PARAMETER_CHANGE`, `ENERGY_CONSUMPTION_CHANGE`, `PRODUCTION_RATE_CHANGE`, `QUALITY_RATE_CHANGE`, `SUPPLIER_DELAY`, `INCIDENT_SEVERITY_CHANGE`, `RESOURCE_AVAILABILITY_CHANGE`, `CUSTOM_SCALAR_CHANGE`.
  - Change Types: `MULTIPLIER`, `PERCENT_DELTA`, `ABSOLUTE_DELTA`, `SET_VALUE`.
  - Values: Finite numeric scalars only (validated against `NaN` and `Infinity`).
- **`ScenarioConstraint`**: Explicit operating thresholds (`MIN_CAPACITY`, `MAX_CAPACITY`, `MAX_UTILIZATION`, `ASSET_AVAILABILITY`, `SUPPLIER_CAPACITY`, `SLA_THRESHOLD`, `QUALITY_THRESHOLD`, `ENERGY_THRESHOLD`, `RESOURCE_THRESHOLD`).
- **`SimulationBaseline`**: Explicit point-in-time reference snapshot identifying source, timestamp, confidence, data quality score, and metric ground truth.
- **`SimulationDelta`**: Computed variance between simulated and baseline states with percentage deltas and status classifications (`UNCHANGED`, `CHANGED`, `UNKNOWN`).
- **`ImpactAssessment`**: Downstream affected domain projections (`CAPACITY`, `DEMAND`, `SUPPLY`, `SLA`, `FINANCIAL`, `SUSTAINABILITY`, `DOWNSTREAM_DEPENDENCY`).
- **`SimulationEvidence`**: Auditable evidence items tracing simulation conclusions back to baseline observations and scenario variables.
- **`SimulationUncertainty`**: Six-dimensional qualitative uncertainty (`overall`, `measurement`, `model`, `scenario`, `dependency`, `data_quality`).

## 4. Baseline Semantics & Sources

Simulations require a defensible baseline grounding. Supported sources:
- **`DIGITAL_TWIN`**: Virtual state snapshot representing physical asset conditions at `snapshot_timestamp`.
- **`SENSOR_FUSION`**: Multimodal fused observation assessment (Prompt 27) providing corroborated physical telemetry.
- **`DEMAND_FORECAST`**: Upstream forecast baseline.
- **`SUPPLIER_RISK`**: Operational supplier baseline.
- **`SLA_CUSTOMER_RISK`**: Customer SLA commitments and baseline risk exposure.
- **`FINANCIAL_IMPACT`**: Financial risk and hourly downtime exposure baseline.
- **`SUSTAINABILITY`**: Energy intensity, emissions, and resource consumption baseline.
- **`KNOWLEDGE_GRAPH`**: Entity relationship and state topology baseline.
- **`EXPLICIT_INPUT`**: Operator-provided analytical parameters.

---

## 5. Temporal Semantics & Future-Leakage Protection

Strict temporal validation is enforced across the simulation lifecycle:
1. **Assessment Timestamp**: Every simulation evaluates at a specific point in time (`assessment_timestamp`).
2. **Anti-Leakage Enforcement**: If any baseline snapshot or observation carries an `effective_at` or `source_timestamp` strictly greater than `assessment_timestamp`, it is rejected with a validation error (`Temporal leakage violation`).
3. **Historical Replay Integrity**: When replaying historical scenarios, only data available at or prior to the simulated timestamp is accessible.
4. **Assumption Expiration**: Assumptions whose `valid_to` timestamp precedes `assessment_timestamp` are flagged as `is_expired = True` and recorded in `SimulationLimitation`.

## 6. Deterministic Simulation Methods & Composition

The simulation engine implements transparent, deterministic equations without black-box ML models or LLM calculations:

### Demand & Capacity Propagation
$$\text{Simulated Demand} = \text{Baseline Demand} \times \left(1 + \frac{\Delta_{\text{pct}}}{100}\right)$$
$$\text{Capacity Gap} = \max\left(0, \text{Simulated Demand} - \text{Production Capacity}\right)$$
$$\text{Capacity Utilization} = \frac{\text{Simulated Demand}}{\text{Production Capacity}}$$

### Asset Availability & Downtime Hours
$$\text{Simulated Availability} = \max\left(0.0, \min\left(1.0, \text{Baseline Availability} \times \left(1 + \frac{\Delta_{\text{pct}}}{100}\right)\right)\right)$$
$$\text{Projected Downtime Hours} = (1.0 - \text{Simulated Availability}) \times \text{Horizon Hours}$$

### Financial Downtime Exposure
$$\text{Simulated Financial Exposure} = \text{Projected Downtime Hours} \times \text{Hourly Downtime Cost}$$

### Sustainability & Emissions
$$\text{Simulated Energy} = \text{Baseline Energy} \times \left(1 + \frac{\Delta_{\text{pct}}}{100}\right)$$
$$\text{Simulated Emissions} = \text{Simulated Energy} \times \text{Grid Emission Factor}$$
*If grid factor is missing, emissions are classified as `UNKNOWN` rather than zero.*

### Scenario Composition & Interactions
When multiple variables affect shared capacity or availability constraints (e.g. demand surge + asset availability reduction), the engine models compounding behavior and labels the interaction effect:
- `SUPER_ADDITIVE`: Compounding stress across demand and asset availability.
- `SUB_ADDITIVE`: Overlapping mitigation.
- `INDEPENDENT`: Orthogonal domains.
- `UNKNOWN`: Unverified interaction relationship.

## 7. Delta Engine & Division-by-Zero Protection

Deltas are computed deterministically:
$$\Delta = \text{Simulated Value} - \text{Baseline Value}$$
$$\Delta_{\text{pct}} = \begin{cases} \frac{\Delta}{|\text{Baseline Value}|} \times 100\% & \text{if } |\text{Baseline Value}| > 10^{-9} \\ \text{undefined (None)} & \text{if } |\text{Baseline Value}| \le 10^{-9} \end{cases}$$

Categorical and state properties evaluate to `UNCHANGED`, `CHANGED`, or `UNKNOWN`.

---

## 8. Bounded Dependency Propagation

Graph traversal and downstream impact propagation are strictly bounded:
- `max_depth = 5` (configurable up to 10)
- `max_nodes = 200`
- `max_paths = 500`
- `max_evidence = 1000`
- `max_variables = 100`

Unbounded recursive graph traversals are structurally prevented.

---

## 9. Deterministic Fingerprinting & Persistence

Simulation results are cryptographically fingerprinted using SHA-256 over:
`tenant_id`, `workspace_id`, `plant_id`, `assessment_timestamp`, `horizon`, canonical sorted targets, canonical sorted variables, canonical sorted constraints, canonical baseline metrics, and method versions.

No non-deterministic inputs (UUIDs, random seeds, wall-clock time, memory addresses) enter the fingerprint calculation. Identical inputs yield identical fingerprints.

Persistence uses an isolated SQLite WAL database (`sage_what_if_simulation.sqlite`):
- Strict parameterized queries.
- Tenant isolation enforced on every query.
- Fingerprint lookup for idempotent deduplication.
- Capped result sets ($\le 200$).

## 10. API Specification

Base Path: `/api/v3/what-if-simulation`

| Method | Path | Required Permission | Description |
|---|---|---|---|
| `POST` | `/api/v3/what-if-simulation/analyze` | `what_if_simulation.analyze` | Evaluates a counterfactual scenario and returns `SimulationResult` |
| `GET` | `/api/v3/what-if-simulation/{simulation_id}` | `what_if_simulation.read` | Retrieves complete simulation result by ID |
| `GET` | `/api/v3/what-if-simulation` | `what_if_simulation.read` | Lists paginated simulation summaries (bounded to 200) |
| `GET` | `/api/v3/what-if-simulation/{simulation_id}/impact` | `what_if_simulation.read` | Returns downstream impact assessments |
| `GET` | `/api/v3/what-if-simulation/{simulation_id}/evidence` | `what_if_simulation.read` | Returns auditable evidence chain |

- **`what_if_simulation.analyze`**: Assigned to `ANALYST`, `OPERATOR`, `MANAGER`, `ADMINISTRATOR`.

## 12. Frontend UI (`WhatIfSimulationModal.tsx`)

The UI is accessible from the OmniHeader bar via the **What-If** button.
Features:
- Clearly labeled `WHAT-IF SIMULATION // V3 COUNTERFACTUAL ENGINE (ANALYTICAL ONLY)`.
- Five interactive views:
  1. **Scenario Builder**: Configure targets, multi-variable changes, and constraints.
  2. **Deltas & State**: Inspect baseline, simulated values, numeric/percentage deltas, and interaction effect.
  3. **Downstream Impacts**: Cards detailing projected capacity gaps, SLA risks, financial exposure, emissions, and affected entities.
  4. **Constraints & Limits**: Clear validation badges (`SATISFIED`, `VIOLATED`, `UNKNOWN`) and transparent limitations.
  5. **Evidence Chain**: Complete auditable traceability linking results to source observations and variables.
- **Strict Execution Isolation**: Zero execute, dispatch, or apply buttons.
